## 秒間クエリ数の参考測定

2026-09-21にRTX830 Rev.15.02.33で測定しました。上流は同一LANの合成DNSサーバー、応答はキャッシュを使わず取得し、上流TCP接続を再利用しています。負荷は外部の公開DNSへ送っていません。

| 応答サイズ・負荷 | 期間・成功数 | 応答時間p50 / p95 / p99 |
|---|---|---|
| 512 B・100クエリ/秒 | 1時間・360,000 / 360,000件 | 14.683 / 19.252 / 21.444 ms |
| 512 B・100クエリ/秒（後続修正後） | 45秒・4,500 / 4,500件 | 14.354 / 18.317 / 20.541 ms |
| 65,535 B・30クエリ/秒（後続修正後） | 45秒・1,350 / 1,350件 | 20.377 / 121.962 / 125.131 ms |

1時間の試験では通信エラー・負荷生成側の取りこぼしは0件で、確立済みの上流接続1本を使い続けました。CPUの観測最大値は全体17%・CPU0 34%・CPU1 1%、装置のメモリ使用率は42%でした。CPU値は5秒平均を5秒間隔で取得したもので、瞬間ピークではありません。最大長応答の45秒試験では、CPUの観測最大値は全体22%・CPU0 44%・CPU1 1%でした。

応答時間には、負荷生成クライアントのTCP接続開始から受信・本文照合・接続終了までを含みます。

これらは**`dns server select`対応前のビルドの実績**です。1時間試験後に修正を加えて短時間試験を行い、その後さらにDNS選択規則対応などを追加しました。公開版そのものに対して同条件の長時間負荷試験は再実施していません。上記を公開版の保証値や限界値とは扱いません。

**RTX830・RTX1210での機能動作は確認済みですが、RTX1210での秒間クエリ数は未測定です。** 実環境では上流の遅延・応答サイズ・キャッシュ率・ルーター上の他の処理によって結果が変わります。

## 公開用ファイルの確認

### 送信元IPごとの制限（2026-09-22追加）

TCP接続4本・平均20問い合わせ/秒・バースト40件を同じ送信元IPで共有する制限を追加しました。接続上限、別IPとの分離、複数接続の合算、再接続後の枠保持と回復、不正・キャッシュ・ローカル問い合わせの計数、SERVFAIL後の既存処理完了と書込期限、管理表の安全な再利用、整数Lua向けの補充計算を10試験で確認しました。続けてRTX830 Rev.15.02.33とRTX1210 Rev.14.01.42で、配布候補ファイルのバイト数・チェックサムと整数Luaでの構文を確認しました。同じソースをTCP/53053・180秒の一時設定で起動し、以下を両機種で確認しました。既存TCP/UDP 53の常設DNSと起動設定は変更していません。

- 同じ送信元IPの4接続は利用でき、5本目は切断される。別IPは正常に利用でき、1本閉じれば同じIPから接続し直せる。
- 2接続にまたがる集中問い合わせで共有クエリ枠を使い切ると、SERVFAILを返して切断する。同時に別IPからは正常に利用できる。
- 2.2秒待機した後、同じIPの再接続と名前解決が成功する。
- 2つの送信元IPv4アドレスから、ローカルA・約4.5KBの外部TXT・通常の外部Aの計12問い合わせが成功する。

集中問い合わせは内蔵DNSの登録名だけを使用しました。RTX830では約0.142秒の間に正常応答60件とSERVFAIL 2件、RTX1210では約0.112秒の間に正常応答40件とSERVFAIL 2件を受信しました。RTXの時計は秒単位のため、RTX830では試験中に秒境界をまたぎ20件分が補充されています。毎秒補充20件・最大蓄積40件という条件内の動作です。これは機能試験であり、長時間負荷試験や同時接続限界の探索ではありません。

全体の32接続はスクリプトが設定した保護上限で、RTX830の同時接続限界の実測値ではありません。既存の100問い合わせ/秒試験も、32本のクライアント接続を維持する容量試験ではありません。RTX830の[`tcp session limit`の初期値15,000](https://www.rtpro.yamaha.co.jp/RT/manual/rt-common/ip/tcp_session_limit.html)は、ルーター自身が終端するTCP全体の設定値であり、LuaによるDNS処理の許容量を保証するものではありません。
