## インターフェース名と用途

7形式の分類は共通ですが、すべての機種にすべての形式があるわけではありません。また、名前の分類に成功しても、機種の設定コマンドとして存在することを保証するものではありません。実際のconfigと状態表示から対象を判断します。

| 名前の形式 | 自機IPv4・状態の読取り | DHCPによるDNS取得元 | `dns host`への直接指定 | `dns host lan`の対象 |
|---|---|---|---|---|
| `lanN` | 対応 | 対応 | 対応 | 含む |
| `lanN/M`（タグVLAN） | 対応 | 対応 | 対応 | 含む |
| `lanN.M`（LAN分割） | 対応 | 未対応 | 未対応 | 含む |
| `vlanN` | 対応 | 対応 | 対応 | 含む |
| `wan1` | 対応 | 対応 | 対応 | 含めない |
| `onu1` | 対応 | 対応 | 対応 | 含めない |
| `bridge1` | 対応 | 対応 | 対応 | 含む |

`N`・`M`は正の整数で、文字列長と値の上限を検査します。全機種のポート数をコードへ埋め込む方式ではありません。PPはこの表とは別に、`dns server pp N`・`dns server select ... pp N ...`の専用構文で扱います。`tunnelN`・`loopbackN`・ISDN用の名前をDHCP取得元やDNSアクセス許可へ追加しません。

直接の`dns host lanN.M`は、公式DNS構文での受理を確認できていないため起動を中止します。従来のパーサーは受理していたため動作変更です。`dns host lan`を使う場合でも、選択したインターフェースの静的IPv4範囲を確定できなければ起動しません。

| 機種・提供環境 | 一般インターフェースとして掲載されている形式 |
|---|---|
| RTX840・RTX3510・RTX1220・RTX830・RTX1210・RTX810・RTX1200・FWX120 | `lanN`、`lanN/M`、`lanN.M`、`vlanN`、`wan1`、`bridge1` |
| RTX1300 | `lanN`、`lanN/M`、`wan1`、`bridge1` |
| RTX5000・RTX3500 | `lanN`、`lanN/M`、`lanN.M`、`vlanN`、`bridge1` |
| NVR700W | `lanN`、`lanN/M`、`lanN.M`、`vlanN`、`wan1`、`onu1`、`bridge1` |
| NVR510 | `lanN`、`lanN/M`、`wan1`、`onu1` |
| NVR500 | `lanN`、`lanN/M`、`wan1` |
| vRX各提供環境 | `lanN`、`bridge1` |

この表は一般的なインターフェース名の対応で、各DNSコマンドの全形式を実機確認した表ではありません。タグVLANやbridgeなどの追加時期は機種・ファームウェアによって異なります。NVR500のタグVLAN・WANはRev.11.00.16以降、RTX3500・RTX5000のbridgeはRev.14.00.12以降です。vRXの提供環境別制約も各製品のマニュアルに従います。[RTX共通の名前一覧](https://www.rtpro.yamaha.co.jp/RT/manual/rt-common/cmdref/cmdref_ifname.html)・[NVRの名前一覧](https://www.rtpro.yamaha.co.jp/RT/manual/nvr700w_nvr510/cmdref/cmdref_ifname.html)

IPv6アドレスの`%lanN`などのスコープ文字列は解析のために識別します。LuaがIPv6で通信する機能ではありません。上流TCPと待受は引き続きIPv4です。

### 一覧にない名前・起動や名前解決の失敗を報告するには

**不具合の報告や「この機種で動いた」という動作報告をいただけると嬉しいです。** [GitHub Issues](https://github.com/Yamar50/rtx-dns-tcp-lua/issues/new/choose)から「不具合の報告」または「動作の報告」を選んで、分かる範囲でご記入ください。

過去には、スクリプトが知らなかった`onu1`がDNS取得元に指定され、起動時に設定解析エラーとなった報告がありました。v0.9.9では上表の形式を検出対象としています。未対応の取得元があっても選択条件を解釈できる場合は、無関係な規則の問い合わせを継続します。そのため、未対応の名前が常にスクリプト全体の起動失敗になるとは限りません。

**一覧にないインターフェース名を使用していて、起動や名前解決に失敗する場合は[GitHub Issues](https://github.com/Yamar50/rtx-dns-tcp-lua/issues)でお知らせください。Luaコードの調査・修正は不要です。** 次の情報があると確認できます。

- 機種名、ファームウェアRev.、使用したスクリプトの版。
- `DNSRELAY`を含むエラーログ。設定行番号が出ていればその番号も含めます。
- 該当する`dns server`・`dns server select`・`dns host`などの設定行と、使っているインターフェース名。

投稿は、GitHubにログインして **Issues → New issue → 報告の種類を選択 → フォームに記入 → 送信** の順です。たとえば「NVR510で起動できない」のように、機種と症状をタイトルにします。コードの変更やPRは不要です。[GitHub公式の投稿手順](https://docs.github.com/ja/issues/tracking-your-work-with-issues/using-issues/creating-an-issue)

正常に動作した機種の報告も歓迎します。機種・ファームウェアRev.・スクリプトの版・確認した問い合わせを添えてください。

設定全体や認証情報は不要です。パスワードなどは記載せず、IPアドレス・ホスト名は必要に応じて伏せてください。APIやアクセス許可設定など、インターフェース名以外の理由で起動を中止する場合もあります。一覧内の名前で失敗するときも、同じ情報を添えてご報告ください。

## 実行環境の条件

現在のスクリプトは、YAMAHA組み込みのLuaと`rt.socket`を使います。外部のLuaSocketや追加ライブラリのインストールは不要です。

必要なAPIには、TCPソケット、`select`、`gettime`、`rt.command`が含まれます。内蔵DNSへ問い合わせる場合はUDPソケットも必要です。`rt.sleep`・`rt.socket.sleep`・`rt.syslog`は補助機能として扱い、不在だけを理由に起動を中止しません。LuaSocketはLua機能版1.06、`rt.command`のログ抑制引数は1.07で追加されています。v1.0.0の再待受に使う`tcp:setoption("reuseaddr", true)`はLuaSocket機能版1.06に含まれ、最低ファームウェア条件は変わりません。表の最低版は両方を満たす版です。vRXの一部旧版は例外があるため、Lua機能版の数字だけでLuaSocketの存在を判断しません。[ヤマハ公式API仕様](https://www.rtpro.yamaha.co.jp/RT/docs/lua/rt_api.html)

ソケットのメソッドは、生成直後に一括検査せず、実際に使う状態で呼び出して確認します。通常の待機は`select`で行い、失敗した場合は`rt.sleep`、`rt.socket.sleep`、空のソケット集合での`select`を利用可能な順に試します。最大3巡の試行で累計1秒以上の待機を確認できれば処理を継続します。待機できない状態ではCPUの空回りを避けるためLuaタスクを停止します。通信に必要なソケットの初期化や時刻取得の失敗、アクセス許可・DNS選択の安全性を確認できない設定については、従来の保護を維持します。

ルーターの機種名を列挙して起動を許可する方式ではありません。表にない機種も、必要なAPIと設定の条件が確認できれば追記します。スイッチ製品は対象外です。通信はIPv4経由で、AAAAレコードの問い合わせとIPv6による通信は区別します。

SRT100は現在使用する`rt.command`のログ抑制引数に非対応のため、上表には含めていません。YSL-V810はRev.1.03.01からAPI条件を満たす参考環境として記録していますが、今回の17機種・提供環境には含めていません。

## 表の更新方法

機種・最低ファームウェア・動作確認状況はこのページでまとめて管理し、READMEと検証資料から参照します。

動作情報がまだない機種の公開表記は「情報をお待ちしております」に統一します。内部の検証記録では未確認として管理し、報告が届いたら確認された版と結果を追記します。

新たな結果は、機種、ファームウェアRev.、スクリプトの版（独自修正があればその内容）、確認日、試験内容、成功・失敗を組にして記録します。LuaとLuaSocketの版も分かれば記録します。確認できなかった項目は「未確認」とし、別の版の成功結果で置き換えません。詳細な試験記録は[検証資料](validation.md)または該当Releaseの説明へ追加します。

最低ファームウェアを変更する際は、必要APIの変更と公式の導入版を確認します。API互換性、設定解析への対応、実機での動作確認を分けて更新します。
