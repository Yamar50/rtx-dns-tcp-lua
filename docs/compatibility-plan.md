# v0.9.9の機種対応仕様と検証方針

[インストールと機能](../README.md) · [技術資料一覧](README.md)

ソースコード・テスト・ドキュメントはすべてOpenAI Codexで生成した。

決定日：2026-09-23。**このページはv0.9.9に実装した仕様と、検証方法を説明します。** YAMAHA RTX830・YAMAHA RTX1210で[機能回帰とネイティブLua解析試験](validation.md#v099-validation)を確認しました。[負荷試験](load-test-v0.9.9.md)では、通常の配布版の送信元IPごとの保護制限を大幅に緩めた条件（4→32接続、20→1,000クエリ/秒、バースト40→1,000件）でRTX830にData Abortによる再起動が1回発生しました。全体32接続の制限は維持しています。既定制限を維持した4台の追加試験では再起動を観測していません。初回の事象は既知の制約として記録し、追加の原因究明は終了しています。配布ファイルの既定制限は維持します。[対応機種の管理表](compatibility.md)には確認した版を分けて記載しています。

同日の[PR #1](https://github.com/Yamar50/rtx-dns-tcp-lua/pull/1)で、利用できない選択規則から後続の規則へ進む変更とNVR510での動作報告をいただきました。比較試験を経て、[IPv6のみの規則に限定して後続select・通常DNSのIPv4へ進む方針](dns-ipv6-fallback.md)を確定しました。PRの利用不能規則を広く読み飛ばす処理は、そのまま採用しません。

**v0.9.9**では回帰・実機・負荷試験と6台への通常配備を確認しました。今後、複数機種での通常利用の結果を確認してv1.0.0へ進みます。軽微な問題が見つかった場合は、それを修正した版をv1.0.0にします。重大な問題や検証が不足する項目が残る場合は、版番号だけを先に進めません。

## 対象

管理表の対応見込み・動作報告・開発時検証の各行、合計17機種・提供環境を実装対象にしています。各行の最低ファームウェア以降で、現在使用するAPIが利用できることを前提にします。vRXは提供環境別に数えます。YSL-V810は参考枠、SRT100とスイッチ製品は対象外です。

対象機種ごとに別のスクリプトを作るのではなく、共通の`rtx-dns.lua`で扱います。対象機種のすべてのDNS関連機能を再実装する計画ではありません。今回の上流DNS取得は固定IPv4・PP・DHCPを対象とし、NVR700WのPDP取得DNSなどは下記の未対応時の処理に従います。

## 決定事項

| 項目 | v0.9.9の実装 |
|---|---|
| 起動対象 | 機種名の許可リストを組み込まない。通信に必要なLua・Socket APIだけを起動時に確認し、ソケットのメソッドは実際に使用する状態で確認する。現在のAPIと非互換の古い環境を補う処理は追加しない |
| インターフェース名 | `lanN`、`lanN/M`、`lanN.M`、`vlanN`、`wan1`、`onu1`、`bridge1`の分類を共通化する。PPは`pp N`の専用構文として扱う |
| 用途ごとの判定 | DNS取得元、状態表示、アクセス許可、自機アドレスの読取りで分類を共用する。名前が存在するという理由だけで、すべてのDNSコマンドの引数として許可しない |
| 番号の扱い | 正の番号と長さ・値の上限を検査する。全機種のポート数一覧は埋め込まず、稼働configと状態表示で指定先を確認する |
| DNS取得元 | 固定IPv4・PP・DHCPの既存選択規則を維持する。未対応インターフェース名だけを理由にスクリプト全体を停止しない |
| 条件を読める未対応規則 | 原則として選択条件に一致した問い合わせをSERVFAILにする。例外として、利用できない理由がIPv6のみと確定した規則は後続selectへ進み、候補がなければ通常DNSのIPv4を使う。無関係な規則の問い合わせは継続する |
| 条件も読めない規則 | その優先順位で対象となり得る問い合わせをSERVFAILにする。規則を読み飛ばして別のDNSへ送らない |
| アクセス許可 | `dns host`の許可範囲を確定できない場合は起動を中止する。未知の指定を全許可に置き換えたり、読み飛ばして許可範囲を広げたりしない |
| 状態表示の差 | 英語・日本語UTF-8・Shift-JISと既知の表示形式を扱い、取得元とDNSアドレスを対応付ける。不明な形式は「未取得」と区別した「判定不能」にする |
| 動的更新 | PP・DHCPの状態確認は30秒ごとを維持する。configそのものは再読込せず、変更後は利用者がスクリプトを再起動する |
| 無関係な設定 | DNS動作や参照するアクセス許可に関係しない設定は無視する。入力全体の長さ・件数上限は維持する |
| DNS補助設定 | `dns service recursive`／`off`、AAAAフィルターなど実際に動作へ影響する設定を維持する。`dns service fallback`など影響しないと確認できた設定は受け入れる。未知の`dns service`を一律に無視しない |
| 障害時の処理 | 起動時のソケット生成・時刻取得・状態読取りの失敗を捕捉し、確保した資源を解放する。ログ出力の失敗で元のエラーを隠さない。ログ・補助待機APIの不在だけでは停止しない。待機失敗時は代替手段を最大3巡試し、待機できない状態が続く場合は空回りせず停止する |
| 資源の上限 | キャッシュ256件・本文1MiB、全体32接続、IP当たり4接続・20クエリ/秒・バースト40件を維持する。小型機種向けに自動で上限を増やさない |
| 検証記録 | API上の対応見込み、協力者の報告、開発時の実機検証を別に管理する。別の機種・ファームウェア・スクリプト版の結果で確認済みにしない |

`dns server select`の番号順、未取得時の代替IP、`restrict pp`、EDNSの指定は[DNS選択仕様](dns-policy.md)に従います。通常DNSは固定DNS・PP・NVRのPDP・DHCPの優先順位を扱います。PDP取得は未対応として保持し、下位DHCPへ迂回しません。IPv6のみの場合の継続条件は[切替仕様](dns-ipv6-fallback.md)に従います。状態表示の取得失敗や取得元の曖昧さを、DNSが明確に未取得である場合と同じ扱いにはしません。

「問い合わせ単位の失敗」は、利用不可となる規則の範囲を限定する意味です。動的取得で宛先や選択条件が変化したときは、現在どおり処理中の問い合わせをSERVFAILで終了し、上流接続とキャッシュを一括更新します。この瞬間は固定DNS規則にも影響します。規則ごとの無瞬断更新は今回追加しません。また、通常の判定不能と状態読取り処理全体の例外は分け、後者では古い宛先へ転送を続けず、既存どおり全体の転送を一時的に利用不可にします。

## インターフェースと利用許可

7形式の一覧は、用途ごとの判定に使う名前の集合です。どの機種にも7形式すべてが存在するという意味ではありません。LAN分割・タグVLAN・ONUなどを扱う際も、実際の設定と公式のコマンド構文に沿って判断します。[共通DNS取得元の仕様](https://www.rtpro.yamaha.co.jp/RT/manual/rt-common/dns/dns_server_dhcp.html)・[NVRのDNS取得元の仕様](https://www.rtpro.yamaha.co.jp/RT/manual/nvr700w_nvr510/dns/dns_server_dhcp.html)

`dns host lan`を理由に、WAN・ONUからの利用を新たに許可しません。アクセス許可の自動生成は、従来どおり設定から確定できるIPv4範囲を使います。選択したインターフェースの範囲がDHCP取得などで確定できない場合は、推測せず起動を中止します。

LAN一括指定はLAN・タグVLAN・LAN分割・VLAN・bridgeを明示した集合として評価し、WAN・ONUの一部の名前だけを除外する判定に依存しません。`lanN.M`はアドレス読取りとLAN一括指定では扱いますが、直接の`dns host lanN.M`は公式の受理を確認できていないため起動を中止します。従来の自動設定パーサーはこの直接指定を受理していたため、ここは動作変更です。`dns server dhcp lanN.M`も対応取得元に含めません。[用途別の対応表](compatibility.md#interface-forms)。`dns host none`では待受を開始しません。参照していないインターフェースのアドレスを読めないことと、実際に許可範囲として選んだアドレスを読めないことも区別します。

`tunnelN`、`loopbackN`、ISDN用インターフェースはDHCPによるDNS取得元の名前へ追加しません。DNSサーバーのIPv4アドレスへの経路がトンネルを通る場合は、通常のルーティングに従います。

## ローカルUDP経路のAPI整合

API調査では、従来のローカルUDP経路が`receivefrom(65535)`を呼ぶ一方、公式仕様の受信上限は2,048バイトという不一致を確認しました。v0.9.9では外部上流へのTCP経路とは分け、次の変更を実装しています。[ヤマハ公式UDP API仕様](https://www.rtpro.yamaha.co.jp/RT/docs/lua/rt_api.html)

- ローカルUDPの受信サイズは2,048バイトにそろえる。
- ローカルへ送る問い合わせにEDNSがある場合は、広告するUDPサイズが2,048を超えるときだけ縮小し、小さい広告値は増やさない。EDNSがない問い合わせへは追加しない。ID・質問・DO/CD・その他のEDNS情報を保持する。
- DNSメッセージとして不完全な応答、または`TC=1`の応答では、完全な回答を得られなかったものとしてSERVFAILを返す。
- ローカル名を外部DNSへ転送したり、自分自身のTCP/53へ再問い合わせしたりしない。
- 外部上流のTCP応答上限65,535バイトと、応答準備完了後からの送信期限2秒は維持する。

v0.1.4は構造が正しいローカル`TC=1`応答をそのままTCPクライアントへ返していました。v0.9.9ではSERVFAILへ変更しているため、通常のローカル名の応答も含めて実機回帰試験を実施しました。

## 今回追加しない機能

- IPv6によるDNS通信、DoT、DoH、NAT46によるDNS応答変換。
- NVR700Wの`dns server pdp wan1`によるDNS取得。PDPはDHCPとは別の取得方式です。構文を判別できる範囲で未対応規則として保持し、該当する問い合わせをSERVFAILにします。[公式PDP設定](https://www.rtpro.yamaha.co.jp/RT/manual/nvr700w_nvr510/dns/dns_server_pdp.html)
- configの自動再読込、ルーター設定の自動変更、PPの接続・切断操作。
- 未確認の状態表示からのDNS推測、アクセス許可範囲の推測、旧APIへの置換。

## 実装と検証の手順

1. 共通のインターフェース名分類を追加し、DNS規則・状態読取り・自動設定へ適用する。
2. 未対応取得元を保持する処理、IPv6のみの場合の後続select・通常DNSへの継続、問い合わせ単位の失敗・起動中止の境界を実装する。
3. 必須APIの確認、初期化失敗時の解放、状態表示の例外処理を整える。
4. ローカルUDPの受信サイズ・EDNS・TC処理を独立して修正する。
5. 合成データと既存の実機証跡に基づく試験を実行し、その後に実機で回帰確認する。

| 試験対象 | 合格条件 |
|---|---|
| 7形式とPP | 正常形式・不正形式・番号境界を検査。名前分類が用途間で食い違わない |
| 未対応DNS取得元 | 該当問い合わせだけSERVFAIL。無関係な既知規則は成功。誤って別のDNSへ転送しない |
| IPv6のみのDNS | 同じ規則のIPv4を優先。IPv6のみなら後続の一致select、次に通常DNSのIPv4、宛先がなければSERVFAIL。判定不能・rejectを迂回しない |
| 読めない選択条件 | 規則の優先順位を保持し、下位のDNSへ漏らさない |
| アクセス許可 | 既存の許可・拒否を維持。判定不能時は待受を開始せず、WAN・ONUへ自動拡大しない |
| 状態表示 | PP/DHCP、複数IF、文字コード、取得・消失・復帰・判定不能を区別。異常表示で全体の未処理例外を起こさない |
| APIと初期化 | 必須API欠如、生成失敗、時刻・select異常、ログ失敗を検査。ソケットを残さずCPUの空回りを防ぐ |
| ローカルUDP | 2,048バイト境界、EDNSの有無とサイズ、DO/CD保持、TC、不正応答、送信元検証を確認 |
| 既存機能 | 大型TCP応答、送信期限、キャッシュ、接続再利用、制限、上流障害、簡易DNS、通常UDPとの共存が維持される |
| 配布ファイル | 共通ファイルを再ビルドし、サイズ差・構文・内容を確認。Releaseには実際の検証版と結果を記載する |

実機確認はRTX830・RTX1210で行いました。v0.9.9のPP・DHCPの状態変化は合成データで検査し、過去版の実回線試験とは区別しています。NVR510では配布する共通ファイルに対する協力者の確認を別途記録します。公開表は公式資料に基づく動作見込みのある機種一覧とし、動作情報がまだない行は「情報をお待ちしております」と表記します。内部では未確認として管理し、結果が届いた機種から確認された版と試験内容を追記します。

### IPoE・PPPoE併用環境を手元に用意できない場合

同じISP契約やIPv6回線を新しく用意することは、今回の開発の前提にしません。DNS取得・選択の処理、実Lua環境でのTCP通信、実際の回線での結果を分けて確認します。

| 確認する部分 | 方法と範囲 |
|---|---|
| DNS取得・選択 | 設定と状態表示の合成データで、先行規則のDNSがIPv6のみ、後続規則がIPv4、通常DNSへの継続、PP切断・復帰、取得失敗、明示拒否、未知の条件を再現。確定したIPv6のみの場合の切替仕様を基準に検査する |
| ルーター上の実通信 | RTX830・RTX1210の試験用実行へ合成した設定・状態表示を渡し、通信には実際のLuaSocketとLAN内のIPv4 DNSサーバーを使う。専用ポートと試験用ACLで、本番DNSやルーターのconfigを変更せずに確認する |
| PPによるDNS取得 | 既存のPP試験環境で実際の状態読取りと取得DNSへの通信を確認する。IPoEとの同時併用の試験とは分けて記録する |
| IPoE・PPPoEの実回線併用 | NVR510の協力者による修正版の動作報告を記録する。最終配布候補を確認いただける場合は、版またはハッシュと結果を対応付ける |

合成データによる試験では、実際のDHCPv6取得、IPoE側DNSへの通信、ISP固有の経路までは検証できません。その範囲は協力者の実機報告として区別し、配布候補で未確認の項目は確認済みにしません。
