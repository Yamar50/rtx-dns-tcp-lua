# 既知の問題

## v0.1.3：レコード数の多い応答が送信前にタイムアウトする（未修正）

2026-09-23、RTX830 Rev.15.02.33とRTX1210 Rev.14.01.42で、約4,000件のAレコードを含む約64KBの正しいDNS応答を受け取ると、単発の問い合わせでもクライアントへ応答を送る前に接続が閉じることを確認しました。

既定の`client_write_timeout=2`では、上流応答の受信後に`client_timeouts=1`が記録され、クライアントはEOFとなりました。一時的に10秒へ変更した診断では、両機種で64,062バイトの応答を正常受信しました。この変更は診断用で、配布ファイルには反映していません。

追加調査では、応答解析中に古くなった時刻を送信期限の起点に使う経路を再現しました。単一TXTレコードの65,535バイト応答は別の試験で成功しており、サイズだけで発生条件は決まりません。

[追加負荷試験報告](load-test-v0.1.3.md)に、再現条件、既定値と診断値の比較、過負荷時の結果を記載しています。ルーター本体のハングや自己再起動は今回の試験では確認していません。

### 開発版の対応（未リリース）

応答の検証・加工・キャッシュ処理・TCPフレーム作成が完了した時点で現在時刻を取得し、その時計値から既定の2秒を計算するよう修正しました。部分送信や後続応答で、先行応答の期限は延長しません。キャッシュTTL・上流問い合わせの期限・既定の制限値も変更していません。

RTX830・RTX1210の一時試験用ポートで、64,062バイト・4,000件のAレコードを含む応答を各5回、既定2秒で正常受信しました。同じ重い要求を4件まとめた試験では、上流応答の待ち期限に達してSERVFAILを返すケースが残っています。今回の変更は送信期限の起点を修正するもので、重複解析の削減や処理順序の変更は含みません。[修正後の検証](validation.md#開発版の送信期限修正未リリース)

GitHub Releaseのv0.1.3配布ファイルは変更していません。

## v0.1.2の問題（v0.1.3で修正済み）

2026-09-23の追加試験で確認した以下の3点は、**v0.1.3で修正しました。** このページにはv0.1.2での発生条件と影響を残しています。[修正内容と更新手順](releases/v0.1.3.md)

| 項目 | 発生条件と影響 |
|---|---|
| キャッシュ対象の判定 | 問い合わせ先のCNAMEと、問い合わせに無関係な名前のAレコードなどを含む応答を、正の応答と誤認して保存する場合があります。必要な回答がない応答が、そのTTLの間再利用される可能性があります。 |
| 複数要求後のTCP半閉鎖 | 同じTCP接続で5件以上の要求をまとめて送り、直後にクライアントの送信側だけを閉じると、応答を返さず接続が閉じる場合があります。影響はその接続の問い合わせです。 |
| DNSクラスの制限 | INクラスを対象とする説明に反し、CHクラスの問い合わせも上流へ転送します。送信元IPのアクセス制限は引き続き適用されます。 |

いずれも**RTX830 Rev.15.02.33とRTX1210 Rev.14.01.42**で再現を確認しました。RTX1300での再現試験は行っていません。

キャッシュの問題は、問い合わせID・質問などが正しく対応する上流応答を受け取った場合の保存判定です。別の名前や別のDNS選択規則のキャッシュを書き換えること、許可されていない送信元から利用することは、今回の試験では確認していません。

アクセス制限、送信元IPごとの接続数・クエリ数制限、不完全な要求のタイムアウト、問い合わせID・質問が一致しない上流応答の拒否は、両機種で正常に動作しました。

v0.1.3では、問い合わせ名からCNAMEをたどって実際の回答を確認してからキャッシュへ保存します。TCP半閉鎖後も受信済みの完全な要求と応答を既存の制限・期限内で処理し、IN以外のクラスにはFORMERRを返して転送しません。

RTX830 Rev.15.02.33とRTX1210 Rev.14.01.42で再試験を行い、各24ケースが成功しました。両機種の整数版Luaでも、問題の応答が保存されず、回答の並び順を変えた正常なCNAME応答は保存されることを確認しています。[検証範囲](validation.md)
