## PP・DHCPの状態に応じたDNS選択を修正

- 英語モードの `Current PPPoE session status is Connected.` を認識できずSERVFAILとなる問題を修正しました。実測した日本語の接続中・非接続・無効・接続処理中の表記も整理しました。
- `restrict pp N` の条件と、DNSを取得するPPの状態を別々に評価します。条件対象が明確に非接続なら後続のselect規則へ進みます。`restrict`がなければ、PP切断だけを理由に規則を飛ばしません。
- IPv4 DHCPのIPリース未取得、または取得元が一意で共通情報からDNS通知なしと確認できる場合は、内蔵DNSの実測に合わせて通常DNSを使います。後続selectの再検索とは区別します。
- PP接続中でもIPCPに通知DNSがなく、内蔵DNSが保持する行内代替DNSを特定できない場合は、通常の固定 `dns server` のIPv4を使います。利用できなければSERVFAILです。この限定した切替ではEDE注記とログを付けます。

選択済みIPv4 DNSのSERVFAIL・タイムアウト・TCP非対応を理由に、後続規則や別の通常DNSへ切り替える機能は追加していません。IPv6のみの規則から後続selectへ進む既存の例外は維持します。[選択条件とEDEの詳細](../dns-policy.md) · [内蔵DNSとの比較](../dns-select-native-compatibility.md)

## 日本語の状態表示を整理

状態文字列の正本を読めるJSONへ集約し、配布LuaにはCP932とUTF-8の比較表を生成します。RTX830・RTX1210で実測した `rt.command()` の日本語はCP932です。UTF-8入力は互換性試験の対象で、両機がUTF-8を返したという意味ではありません。CP932の後続バイトをASCIIの英字と誤って小文字化しないようにしました。

## 実機試験と制限

RTX830 Rev.15.02.33とRTX1210 Rev.14.01.42で回帰確認を行い、RTX1210では実PPPoEとDHCP、公開用設定の自動再読込も確認しました。RTX830では送信元制限を緩めた飽和試験を含め、負荷を止めた後の復帰を確認しています。件数・配布設定との差・候補ファイルのSHA256は[試験結果](../results/v1.0.1-2026-10-08.md)に記載しています。

複数IPv4 DHCP取得元の共通DNS欄を特定IFへ対応付けられない場合、必要な状態表示が欠ける場合はSERVFAILです。RTX1300では協力者から修正後のTCP回答・大型TXTの取得成功が報告されています。過去の他機種の動作報告をv1.0.1の確認へ読み替えません。[残る制約](../known-issues.md)

2026-10-08、[しよさん（@udp_5060）](https://x.com/udp_5060)からRTX1300でv1.0.1が正常に動作したとの報告をいただきました。**実機での検証と問題の切り分けへのご協力、ありがとうございます。** [報告と確認範囲](../compatibility.md#rtx1300-v101-report)

設定の自動再読込、簡易DNS、アクセス制限、送信元ごとの制限、キャッシュ、応答準備後2秒の送信期限は維持しています。
