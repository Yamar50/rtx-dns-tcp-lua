# 内蔵DNSの実PPPoE選択試験（2026-10-08）

ソースコード・テスト・ドキュメントはすべてOpenAI Codexで生成した。

## 対象と方法

- 対象：YAMAHA RTX1210 Rev.14.01.42の**内蔵UDP DNS**。Luaは動かしていない。
- 対向：GL.iNet GL-AR300M、OpenWrt系ファームウェア、rp-pppoe-serverとpppd。専用LANで実際のPPPoEセッションとIPCPのDNS通知を使用した。商用ISP・NGN網全体の再現ではない。
- 比較基準：公開済みv1.0.0。修正候補の実通信試験ではなく、v1.0.1で合わせる選択動作の確認。
- 2026-10-08 01:13～01:19 JSTに18ケースを実施。前後の通常DNSの正常対照2件と、状態別16件。準備中の中断・経路不備があった試行は、この18ケースに含めない。
- 質問は毎回異なる試験用名のAレコード。内蔵キャッシュを無効化し、UDPのみ・1回の要求で観測した。規則1（dns server select 1）はAAAA対象のため一致しない。
- 規則2（dns server select 2）のPP取得DNS、規則3（dns server select 3）の固定DNS、通常DNSを別の宛先にし、送信先側のログを確認した。無応答の観測時間は35秒、接続中の無応答ケースは45秒。

## DNS通知なしのケースで残った疑問

9～13では、現在の`IPCP Local`にDNS項目がないことを確認した。それでも、8で行内代替に指定したDNS Bへ問い合わせが届いた。9・10・13では現在のselect行にもDNS Bはない。

**「状態表示に通知DNSがない」ことと「内蔵DNSに問い合わせ先が残っていない」ことは同義ではない。** 直前の設定・取得履歴の保持が原因候補だが、この試験では内部の保持規則までは特定していない。履歴のないPP作成直後の状態と、設定順序を変えた状態で追加確認する必要がある。この5件を根拠に、常に行内代替を使う／無視する、常に通常DNSへ進む、といった一般則は確定しない。

## 試験経路と復元

準備中、IPCP通知DNSと行内代替DNSのアドレスに対して、PPを経由する一時的なホスト経路が追加されることを観測した。試験元や管理接続元をそのDNSアドレスと兼用すると、返信経路まで変わり、選択処理の誤りに見える。この18ケースでは、問い合わせ元・SSH管理元とPP側DNSを分離した。初期の経路不備やSSH中断を、ルーターの再起動やDNS選択の試験結果として扱っていない。

終了後、稼働configの全設定行の一致、起動時刻、Luaタスク、`/lua`のファイル一覧が試験前と同じことを確認した。設定の`save`は行っていない。保存configの一覧メタデータは不変だが、保存config本文の同一性を読み出して検証したものではない。対向の試験用PPPoEサーバとDNS待受は停止し、一時アドレス・フィルターの除去と元のDNSサービス再開を行った。

## 最初の18ケースで確認していない範囲

- 改修後LuaのTCP中継との同条件比較、TCP接続だけ失敗する上流。
- 履歴のないDNS未通知、PP接続処理中の選択、認証失敗、物理切断や無応答検出による自然なPP切断。
- 異なるプライマリ／セカンダリDNS間の選択、SERVFAIL以外のエラー応答。
- DHCPの未確定条件、複数DHCP取得元の対応付け、DHCPv6・ONU、RTX1300の修正後確認。

Luaの最終失敗を既定の期限でSERVFAILにする方針は維持する。内蔵UDPが35～45秒無応答だったケースに合わせて、Luaの処理期限を延ばす要件にはしない。

## 追加：日本語の状態表示とLuaの文字コード

同日、RTX1210 Rev.14.01.42と、PPPoE接続中のRTX830 Rev.15.02.33で、採取用Lua内の表示言語を切り替え、`rt.command("show status pp N", "off")`の返す生バイト列を記録した。RTX830では接続操作・DNS設定変更を行っていない。

| Lua内で指定した設定 | RTX1210の取得バイト列 | RTX830の取得バイト列 |
|---|---|---|
| `en.ascii` | 英語ASCII | 英語ASCII |
| `ja.sjis` | 日本語CP932 | 日本語CP932 |
| `ja.utf8` | 日本語CP932 | 日本語CP932 |
| `ja.euc` | 日本語CP932 | 日本語CP932 |

これは上記2機種・FWの`rt.command()`返却値の実測である。コンソール画面自体の文字コードや、全機種のAPI動作が同じだとする結論ではない。[コンソール言語設定の公式説明](https://www.rtpro.yamaha.co.jp/RT/manual/rt-common/setup/console_character.html)と、Luaが受け取った実際の文字列は分けて扱う。

RTX1210では以下の日本語を採取した。表記は実機の出力どおり。

| 現在の状態 | 日本語の状態文 |
|---|---|
| PP無効 | `PPPoEセッションは現在使用できません` |
| 一度も接続していない | `PPPoEセッションは一度も継っていません` |
| 切断後 | `PPPoEセッションは継っていません` |
| 接続中 | `PPPoEセッションは接続されています` |
| 接続処理中 | `PPPoEセッションは接続処理中です` |

切断後には`直前のPPPoEセッションの状態:`という履歴欄も続く。現在の状態と混同しないことをv1.0.1の解析要件とする。未接続の表示は最初の採取試行で確認し、接続履歴ができた後の表示と区別して保存した。

RTX830の日本語CP932をv1.0.0とローカル修正候補の解析器へ入力すると、どちらも接続中・IPCP DNS2件と判定した。一方、RTX1210の無効・切断表示は未認識となり、実測表記の追加が必要である。これはホスト上での解析再生であり、改修後Luaの実機DNS通信試験ではない。

採取用Luaの言語指定は設定にも影響する。初回は設定差分ガードで停止したため、言語以外の差分がないことを照合して復元し、同じLua内で採取直後に元の言語へ戻す手順に変更した。新規SSH接続でも復元を確認して再試験した。製品スクリプトがルーターの表示言語を変更する仕様は追加していない。

## 追加：通知DNSなし・行内代替DNSと接続の順序

最初の18ケースで残った疑問を調べるため、今回の試験で通知DNS・行内代替DNSを与えていない別のPP番号から始めた。12ケースの追加比較に続き、さらに別のPP番号で、試験用DNSへの経路を明示した10ケースの対照を完了した。後者では通常DNSとPP側の2つのDNSへ固定selectで到達できることを先に確かめ、DNS未取得による自動経路の不在とDNS選択を分離した。いずれも正常対照と意図した無応答を含む件数である。

| 条件 | 経路を明示した対照での観測 |
|---|---|
| 行内代替なし・DNS通知なしで接続 | 35秒以内に回答なし。後続select・通常DNSにも到達しない |
| 接続を維持したまま行内代替DNSを追加 | 同じく到達なし。宛先への経路があっても使用しない |
| その行内代替を削除 | 同じく到達なし |
| 行内代替DNSを設定してから接続、DNS通知なし | 行内代替DNSを使用しNOERROR |
| 上記の接続を維持して行内代替を削除 | 削除した代替DNSを引き続き使用しNOERROR |
| 行内代替を削除した状態で再接続、DNS通知なし | 35秒以内に回答なし。経路が残っていても、以前の代替・後続・通常DNSには到達しない |

この時点で、**接続前後の設定順序によって、同じ現在config・IPCP表示でも選択先が違う**ことを確認した。単なるキャッシュ命中ではなく、各質問は別名で、内蔵キャッシュも無効である。通常DNSがあるだけでは、通知DNSのないPP規則から通常DNSへ移らない。

PPセッション単位で行内代替の情報を保持していることが有力な説明だが、内部データ構造を確認したものではない。現在のconfigと`IPCP Local`の通知DNS欄だけから、途中起動したLuaが保持先を必ず復元できるとはいえない。v1.0.1の要件では、内蔵DNSの観測と、Lua側でその状態を取得できるかを別の課題として管理する。

追加試験でも、終了後の稼働config・起動時刻・Luaタスク・ファイル一覧・保存config一覧メタデータを照合した。設定の保存は行っていない。改修後Luaとの実通信比較と、DHCPの未確定項目を解決した試験ではない。
