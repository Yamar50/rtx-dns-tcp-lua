## PP選択とEDE

隔離したPPPoEサーバーと、宛先・UDP/TCP・質問名を記録する模擬DNSを使用しました。内蔵DNSのUDP経路とLuaのTCP経路を分けて確認しました。

| 条件 | 結果 |
|---|---|
| 接続中、IPCPからDNS通知あり | 通知されたDNSへ送信 |
| 通知先からSERVFAIL、無応答、TCP側のみ応答なし | 後続selectや通常DNSへ送らない。Luaは最終的にSERVFAIL |
| `restrict pp`付きで切断 | 内蔵DNS・Luaとも後続の該当selectを使用 |
| `restrict`なしで切断 | Luaは後続規則へ迂回せずSERVFAIL |
| 接続中・通知DNSなし | Luaは通常の固定DNSへ直接送信し、EDNS付きクライアントへEDEを付加 |
| 固定DNSからNXDOMAIN | RCODEを維持してEDEを付加 |
| 固定DNSのSERVFAIL・無応答・設定なし | SERVFAILとEDE。後続selectへ送らない |
| EDNSなしのクライアント | 応答するがEDEを付けない |
| 上流側だけEDNS無効 | EDNS対応クライアントへのEDEを確認 |
| 同じ質問を再送 | 上流への送信が1回のまま、TTLが減ったキャッシュ応答にもEDEを付加 |
| 通知DNSを再取得 | 約30秒の更新後に通知DNSへ戻り、代替経路のEDEを解除 |
| 接続時の行内代替DNSを内蔵DNSが保持 | 内蔵DNSは保持先、Luaは決定済み例外の通常固定DNSを使用。両者が意図的に異なることを確認 |

最後の条件で、最初の試行に上流TCP接続タイムアウトを1回観測し、LuaはEDE付きSERVFAILを返しました。追加の新規質問10回はすべて正常で、原因は特定できていません。DNS選択先を誤った証拠ではありませんが、再現しなかったことを修正済みの証明とはしません。

## DHCPの差を検出して修正

最初は2つのIPv4 DHCP取得元を持つ試験機で、内蔵DNSが応答する一方、Luaが取得元不明としてSERVFAILになりました。既存の複数IF制約と、DNS通知なしの選択を分離するため、他のDHCP取得元を試験中だけ外し、最後に戻しました。

1取得元・IP取得済み・共通情報にゲートウェイあり・DNSオプションなしでは、内蔵DNSは通常固定DNSを使用しました。候補Aは行内代替IPを使ったため、候補Bで修正しました。候補Bでは両経路が通常固定DNSを使い、DNS通知を追加した再取得後は両経路が通知先を使うことを、宛先側の記録でも確認しました。

セカンダリーIPだけで到達させようとした最初の試験設備は対照問い合わせに応答せず、その試行は中断・復元しました。製品のDHCP選択結果として数えていません。

複数IFのDNS対応、共通情報の省略、DHCPv6・ONU、自然なリース失効はこの単一IF試験では確認していません。IP未取得の内蔵DNSの挙動は[10月7日の記録](native-select-2026-10-07.md)を参照してください。

## 回帰と公開設定

両機種で各32項目が成功しました。ACL、送信元ごとの接続数・クエリ数制限、不正なTCP長、不正なDNS、分割受信と半閉鎖、上流のID・質問・圧縮ポインター不整合、キャッシュ汚染に関連する応答判定、キャッシュ世代の変更、障害復帰、DO/CD、ローカルUDPの2,048バイト制限を含みます。試験用TCP/53053と合成上流を使用し、既定制限を維持しました。

65,535バイトの応答を全バイト比較しました。4,000件のAレコードを含む64,067バイトの応答は、新規接続の単発5回ずつで成功しました。全処理時間はRTX830で2.18～3.02秒、RTX1210で2.07～5.02秒でした。これは問い合わせ全体の時間であり、応答準備後に始まる既定2秒の送信期限とは異なります。

最終候補Bの公開用設定をRTX1210のTCP/53で実行し、通常A、512バイトを超えるTXT、簡易DNSの追加・変更・削除、ACL変更による拒否と復帰を確認しました。約30秒の設定確認で反映し、試験後は元の本体・設定へ戻しました。

ホストでは19本のLua試験とPython 52試験が成功しました。RTX1210の整数版Lua 5.1では、PP/DHCP状態、選択、EDE加工、IPv6専用時の切替に関する1,774チェックが成功しました。日本語CP932の実測フィクスチャとUTF-8互換入力を区別しています。

## RTX830の飽和試験

常用TCP/53を維持し、TCP/53053の試験用スクリプトを並行実行しました。送信元は2つ、合成上流を使用し、UDP洪水試験は行っていません。

| 制限 | 配布設定 | 診断用の緩和設定 |
|---|---:|---:|
| 送信元IPごとの同時接続 | 4 | 32 |
| 送信元IPごとのクエリ/秒 | 20 | 1,000 |
| 送信元IPごとのバースト | 40 | 1,000 |
| 全体の接続／保留要求 | 32／32 | 32／32（維持） |

候補Aでは新規TCP接続を使う各15秒の20段階と、32本のTCP接続を再利用する各25秒の8段階を実施しました。候補Bでは飽和する2条件を各25秒で再確認しました。全30段階後に通常問い合わせへ復帰し、再起動・ハング・不正な完全DNS応答を観測しませんでした。

| 代表条件 | 予定QPS | 予定件数 | 正常応答数 | 補足 |
|---|---:|---:|---:|---|
| A・既定制限・512B・新規接続 | 40 | 600 | 600 | 全件成功 |
| A・既定制限・65,535B・新規接続 | 40 | 600 | 600 | 全件成功 |
| A・緩和設定・512B・新規接続 | 500 | 7,500 | 2,639 | 過負荷による拒否等あり |
| A・緩和設定・65,535B・新規接続 | 160 | 2,400 | 246 | タイムアウト1,844件。その後復帰 |
| B・緩和設定・512B・32接続再利用 | 2,000 | 50,000 | 5,631 | 実送信5,631、空き待ちによる未送信44,369 |
| B・緩和設定・65,535B・32接続再利用 | 320 | 8,000 | 895 | 実送信895、空き待ちによる未送信7,105 |

Bの2条件では実送信した要求はすべて正常応答し、タイムアウト・再接続は0でした。予定QPSをルーターの処理性能と解釈しないでください。新規接続と再利用接続、応答の大きさ、制限で結果が変わります。CHクラスの高頻度試験も実施していますが、その成功件数は期待したFORMERRの件数で、名前解決成功数には含めません。

全段階の予定数・開始数・実送信数・応答・タイムアウト・生成側の未送信は[測定CSV](v1.0.1-load-2026-10-08.csv)に掲載しています。候補Aの負荷試験で `show environment` のCPU 5秒値は最大49%、本体メモリ使用率は43～53%でした。これはサンプリングした全体値で、CPUコア別の瞬間最大値やメモリリークがない証明ではありません。旧版で発生した[Data Abortの原因](../known-issues.md#v099-overload)が解消したとも判断しません。

診断設定に上限外のレート値を誤って指定した準備試行では起動せず、復元してから正しい値で試験しました。制限外の値で製品が動作した結果として数えていません。
